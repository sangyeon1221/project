# ScholarMind

논문을 찾아 읽고 답해주는 RAG 어시스턴트입니다. 전용 그래픽카드 없이 일반 노트북에서 돌아가며, 노트북에 기본으로 들어 있는 내장 그래픽으로 추론을 가속합니다.

질문을 입력하면 Semantic Scholar에서 관련 논문을 검색하고, 신뢰도를 따져 한 편을 고른 뒤, PDF를 받아 인덱싱하고 그 내용에 근거해서 답합니다. 클라우드 API로 추론하지 않기 때문에 질문 내용이 외부 모델 서버로 나가지 않습니다.

졸업 작품인 [Ragxiv](../ragxiv)의 후속 버전입니다. Ragxiv는 arXiv에서만 검색했는데, 실제로 써보니 세 가지가 걸렸습니다. 심사를 거치지 않은 논문이 대부분이라 신뢰도를 판단할 수 없었고, 의미 기반 검색만으로는 약어나 고유명사를 놓쳤으며, 답변이 완성될 때까지 화면이 멈춰 있었습니다. 이 버전은 그 셋을 해결한 결과입니다.

## 동작 방식

"방금 논문 요약해줘" 같은 **후속 질문이면 새로 검색하지 않고** 이미 인덱싱된 논문을 씁니다. 키워드로 대부분 걸러내고 애매할 때만 LLM에 물어봅니다. 반대로 "다른 논문 찾아줘", "최신 논문 가져와줘"처럼 새 논문을 달라는 말이면 이 판단보다 먼저 새 검색으로 보냅니다.

"컴퓨터"처럼 한 단어뿐인 질문은 검색하기 전에 무엇이 궁금한지 되묻습니다. "개념 설명", "최신 연구", "그대로 검색" 버튼 중 하나를 누르면 바로 진행됩니다.

새 주제라면 이렇게 진행합니다.

1. LLM이 질문을 검색용 영어 키워드 3개로 바꿉니다. 질문에 있던 약어가 빠지면 되살리고, "MCP가 뭐야?" 같은 정의 질문이면 개요 논문을 찾는 검색어를 앞에 넣습니다
2. 구문별로 나눠 Semantic Scholar를 검색하고 결과를 병합합니다. "최신", "요즘" 같은 말이 있으면 작년 이후 논문만 검색합니다. "제일 최신"이면 올해 논문부터 찾고, 없으면 작년 이후 → 제한 없음 순으로 넓힙니다
3. 신뢰도 필터로 후보를 거르고, PDF를 구할 수 없는 논문은 미리 제외합니다
4. LLM이 초록을 읽고 한 편을 고릅니다. 맞는 논문이 없다고 판단하면 화면에 경고를 띄웁니다. 고른 논문의 PDF를 못 받으면 질문과 가장 가까운 다음 후보로 넘어갑니다
5. PDF를 받아 1,000자 단위로 쪼개고, 참고문헌 부분은 빼고 FAISS와 BM25에 넣습니다
6. 두 검색 결과를 합쳐 상위 5개를 고르고, 질문과 관련된 문장만 남겨 논문 초록과 함께 LLM에 넘깁니다
7. 답변을 토큰 단위로 출력하면서 출처를 함께 보여줍니다. 출력이 끝나면 같은 내용을 어미만 바꿔 반복한 줄을 지우고, 수치를 원문과 다른 의미로 옮긴 곳이 있으면 원문 문장과 함께 경고합니다
8. 답변 아래에 검색된 후보 논문 목록(날짜·학회·인용 수·한 줄 요약)을 보여줍니다. 자동으로 고른 논문이 원하던 것이 아니면 **[이 논문으로 답하기]**를 눌러 같은 질문에 다른 논문으로 다시 답하게 할 수 있습니다

## 구성

| | |
|---|---|
| 추론 | Ollama + EXAONE 3.5 2.4B (로컬, 내장 그래픽 가속 · 없으면 CPU) |
| 임베딩 | `intfloat/multilingual-e5-small` (384차원) |
| 검색 | FAISS `IndexFlatIP` + BM25, RRF로 융합 |
| 논문 | Semantic Scholar API |
| PDF | arXiv · openAccessPdf · Unpaywall · CORE 순차 시도, PyMuPDF로 추출 |
| UI | Streamlit |

## 만들면서 겪은 것들

**검색이 실패하는데 원인을 알 수 없던점.** 같은 질문이 어떤 날은 결과를 가져오고 어떤 날은 "논문을 찾을 수 없다"고 나왔습니다. API를 직접 호출해보니 429였습니다. Semantic Scholar는 API 키 없이 쓰면 전 세계 사용자가 공유하는 요청 풀에 들어가는데, 이게 거의 항상 포화 상태였습니다.

문제는 코드가 429를 받으면 그냥 빈 목록을 반환했다는 점. 호출한 쪽에서는 "논문이 없다"와 "API가 막혔다"를 구분할 수 없었고, 결국 사용자에게 "질문을 바꿔보세요"라고 잘못 안내하고 있었습니다. 지금은 429를 별도 예외로 올려서 화면에 요청 한도 초과라고 정확히 표시하고, 첫 실패에서 즉시 중단해 남은 할당량을 낭비하지 않습니다.

**의미 검색만으로는 부족했던점.** 밀집 벡터는 "환각"과 "hallucination"이 같은 뜻인 걸 알아채지만, `QMIX` 같은 알고리즘 이름은 의미로 압축하는 과정에서 뭉개집니다. 그래서 단어를 그대로 세는 BM25를 함께 돌리고 두 순위를 RRF로 합쳤습니다. 점수 체계가 서로 달라 그냥 더할 수 없는데, RRF는 점수 대신 등수만 쓰기 때문에 정규화가 필요 없습니다. BM25는 신경망이 아니라 CPU 부담도 거의 없습니다.

한참 뒤에야 알았는데, **한국어 질문에서는 BM25가 사실상 꺼져 있었던점.** BM25는 단어가 그대로 일치해야 점수를 주는데, 질문은 한국어이고 논문 본문은 영어라 일치하는 단어가 하나도 없었던 겁니다. 하이브리드 검색을 넣은 이유가 한국어 질문에서는 작동하지 않고 있었습니다. 지금은 논문을 찾을 때 쓴 영어 키워드를 질문과 함께 BM25에 넘깁니다.

**요약을 시켰더니 부록을 요약했던점.** 진화 전략을 다루는 논문에 "요약해줘"라고 했더니 "이 논문은 강화학습 하이퍼파라미터 조합에 초점을 맞춥니다"라고 답했습니다. 부록의 실험 설정 표가 검색된 것이었습니다. 원인은 "요약해줘"라는 말 자체에 검색할 단서가 없다는 점이었습니다. 유사도 검색이 사실상 아무 문단이나 집어온 겁니다. 지금은 요약 의도가 감지되면 유사도 검색을 건너뛰고 문서 앞부분을 씁니다.

**한국어 답변만 형식을 안 지켰던점.** 프롬프트에 불릿으로 쓰고 번호는 쓰지 말라고 했는데, 영어는 지키고 한국어만 매번 `1. 2. 3.`으로 나왔습니다. 소형 모델이 한국어 생성에서 형식 지시를 놓치는 것 같았습니다. 프롬프트에 출력 예시를 넣고, 그래도 번호가 나오면 후처리로 바꾸도록 했습니다. 다만 `3.5배` 같은 소수점이 망가지지 않게 줄 맨 앞에만 적용합니다.

**외부 데이터가 틀린 경우도 있었던점.** Semantic Scholar가 알려준 arXiv 번호가 전혀 다른 논문을 가리키는 사례를 만났습니다. 화면에는 A 논문 제목이 뜨는데 저자와 연도는 B 논문 것이었습니다. 남의 데이터베이스라 고칠 수는 없지만 탐지는 됩니다. arXiv 번호는 앞 네 자리에 제출 연월이 들어 있어서, 논문의 게재 연도와 대조하면 어긋나는 걸 잡을 수 있습니다. 차이가 크면 인용 정보 옆에 경고를 띄웁니다.

**"MCP가 뭐야?"라고 물었더니 엉뚱한 답이 세 겹으로 나왔던점.** 하나씩 뜯어보니 원인이 전부 달랐습니다.

- **모델이 MCP를 몰랐던점.** MCP(Model Context Protocol)는 2024년 11월에 발표되어 2025년에 퍼진 개념인데, EXAONE 3.5는 그 직후에 공개된 모델입니다. 모르는 약어를 `Multi-Agent Systems`로 짐작했고, 검색부터 빗나갔습니다. RAG는 모델이 모르는 지식을 논문에서 가져오려는 방식인데, 정작 질문을 검색어로 바꾸는 단계는 모델 자신의 지식에 기대고 있었던 겁니다. 그래서 질문에 있던 약어가 키워드에서 사라지면 `MCP AI`처럼 되살리도록 했습니다. `MCP`만으로 검색하면 생물학 약어와 섞이는데, `AI`를 붙이니 5편 모두 맞는 논문이 나왔습니다.
- **약어 뜻을 지어냈던점.** 답변에 "MCP(Multi-Component Processing)"라는, 어디에도 없는 풀이가 나왔습니다. 문맥에 풀이가 없으면 약어를 그대로 쓰도록 했습니다.
- **참고문헌을 논문 내용으로 읽었던점.** "이 논문은 Teamcraft에 초점을 맞춘다"고 답했는데, PDF를 확인해보니 Teamcraft는 참고문헌 목록에 딱 한 번 나오는 다른 논문의 제목이었습니다. 논문의 실제 주제(MAST)는 141번 나옵니다. 참고문헌은 논문 제목이 빽빽하게 나열되어 있어 키워드가 잘 걸립니다.

참고문헌을 빼는 건 생각보다 까다로웠습니다. 처음엔 "References" 제목에서 잘라냈는데, 장마다 참고문헌이 있는 문서에서 본문 절반을 날렸고, 부록 제목이 특이한 논문에서는 아무것도 못 잘랐습니다. 그래서 위치 대신 형식을 보도록 바꿨습니다. `Sun, F.`, `(2022).`처럼 참고문헌에만 반복되는 패턴을 세서 청크 단위로 판별합니다. 본문의 `(Sun et al., 2022)` 같은 인용에는 걸리지 않게 했고, 정답을 아는 논문에서 참고문헌 23개 중 22개를 잡고 본문·부록 137개 중 1개만 잘못 잡았습니다.

이렇게 고치니 검색은 맞게 됐는데, 이번엔 MCP를 의료에 응용한 사례 논문이 뽑혀 "뇌 발달에 중요한 단백질을 모니터링한다"는 답이 나왔습니다. 사례 연구의 배경 문장을 플랫폼의 기능으로 착각한 것입니다. 두 가지를 더 했습니다. 답변할 때 **논문 초록을 항상 함께 넘겨** 모델이 문단을 해석할 기준점을 갖게 했고, **정의를 묻는 짧은 질문이면 개요·서베이 논문을 우선**하게 했습니다. 지금은 MCP를 다룬 서베이 논문을 골라 "Anthropic이 2024년에 도입한 오픈 표준 프로토콜, JSON-RPC 기반 클라이언트-서버 구조"라고 답합니다.

**답변 한 줄을 빈 문장으로 채웠습니다.** 세 줄 중 하나를 "구체적인 내용은 제한적으로 다루고 있습니다"처럼 논문을 평가하는 문장으로 채우는 경우가 잦았습니다. 근거를 못 찾았다는 신호인데 답변처럼 보입니다. 각 줄이 문맥의 구체적인 사실 하나를 담도록 했고, 논문 선택 단계에서 이미 "직접 다루지 않는다"고 판단한 경우에는 답변 앞에 경고를 띄웁니다.

**"최신 논문을 가져와줘"라고 했더니 방금 읽은 논문으로 답했습니다.** "AI 최신 트렌드"를 물은 뒤 이어서 물은 질문인데, 문장에 "논문"이 들어 있어 후속 질문으로 분류된 것이었습니다. 새 논문을 달라는 표현("가져와", "찾아줘", "다른 논문")은 후속 질문 판단보다 먼저 보도록 했습니다. 다만 "이 논문에서 실험 결과 찾아줘"는 후속 질문이 맞으므로, 지금 논문을 가리키는 말이 함께 있으면 새 검색으로 보내지 않습니다.

새 검색을 해도 "최신"은 반영되지 않았습니다. 코드에는 최신순 정렬을 요청하는 기능이 있었는데, 확인해보니 Semantic Scholar의 검색 API는 이 정렬 옵션을 **오류 없이 무시**하고 있었습니다. 대신 연도 필터는 실제로 동작해서, 최신 의도가 보이면 작년 이후 논문만 검색하도록 바꾸고 동작하지 않던 정렬 코드는 지웠습니다. 같은 질문으로 다시 돌려보니 후보 9편이 모두 2025년 논문이었습니다.

그런데 "AI 관련 제일 최신 논문을 찾아줘"에서는 엉뚱한 논문들이 나왔습니다. LLM이 "최신"을 `AI latest advancements`, `cutting-edge AI research`처럼 검색어에도 넣어서, 제목에 "Advancements"가 들어간 논문이 후보를 채웠습니다. 비스무트 나노구조 화학 논문까지 섞였습니다. 연도 필터가 이미 "최신"을 맡고 있으므로, 최신 의도일 때는 검색어에서 이런 시기 표현을 뺍니다. 단, `modern Hopfield networks`, `novel view synthesis`처럼 기술 이름의 일부인 단어는 남깁니다. 또 "제일 최신"이면 올해 논문부터 찾고, 선택할 때 후보를 날짜순으로 보여주면서 "주제와 관련 있는 것 중 가장 최근 것"을 고르게 했습니다. 고친 뒤에는 후보가 Nature, IEEE 등 2026년 논문 6편으로 바뀌었고, 그중 가장 최근(6월) 논문을 골랐습니다.

같은 사례에서 고른 논문의 PDF를 받지 못하자 목록 맨 앞 논문으로 넘어갔습니다. 지금은 질문과 가장 가까운 후보부터 시도합니다. 또 "논문을 찾아줘"는 논문 한 편의 설명이 아니라 논문 자체를 원하는 요청이라, 답변 아래에 후보 목록을 날짜·학회·인용 수와 함께 최신순으로 보여줍니다.

**찾던 논문이 후보 2위에 있었는데 다른 논문으로 답했습니다.** Semantic Scholar에서 본 *Towards end-to-end automation of AI research*(Nature, 2026)를 찾으려고 "end to end automation이 뭐야?"라고 물었습니다. 검색은 그 논문을 2위로 찾았지만, LLM은 초록에 "end-to-end ML automation"이라는 표현이 그대로 들어 있는 MLZero를 골랐습니다. 질문에 "AI 연구"라는 말이 없었으니 모델로서는 틀린 선택이 아닙니다. 자동 선택은 아무리 고쳐도 빗나갈 때가 있어서, 답변 아래에 후보 목록을 항상 보여주고 다른 논문을 골라 같은 질문에 다시 답하게 했습니다. 고르는 데 필요한 정보는 Semantic Scholar가 주는 한 줄 요약(TLDR)으로 채워서 LLM 비용이 들지 않습니다. 여러 편을 골라 각각 요약하는 방식도 검토했지만, 논문마다 다운로드·인덱싱·답변이 반복되어 느린 와이파이에서 1분을 넘기기 쉬워 택하지 않았습니다. 자동 선택과 직접 선택을 모드로 나누는 것도 검토했지만, 결과를 보기 전에는 어느 쪽이 맞는지 알 수 없어서 자동 선택을 기본으로 두고 버튼으로 바꾸게 했습니다.

이 과정에서 정의 질문 판정이 한국어 글자 수 기준이라 "end to end automation이 뭐야?"처럼 영어 용어가 긴 질문을 놓친다는 것도 알게 됐습니다. 고쳤더니 이번엔 서베이 검색어(`end-to-end automation survey`)가 붙으면서, "Kilo Degree Survey"(천문 관측) 같은 논문이 후보를 채우고 원래 2위였던 논문이 사라졌습니다. 서베이 검색어는 MCP처럼 **용어가 한 단어일 때만** 붙이고, 개요 논문 표시도 "A Survey of …"처럼 실제 서베이 제목 형태일 때만 붙이게 고쳤습니다.

트렌드 질문에는 문제가 하나 더 있었습니다. 근거는 논문 한 편인데 답변은 "AI의 최신 트렌드는 ~입니다"처럼 분야 전체의 사실인 양 말했습니다. 분야 전체를 묻는 질문이면 "이 논문은 ~ 관점에서"처럼 범위를 밝히고 일반화하지 말라는 규칙을 넣었습니다. 소형 모델이라 첫 줄은 지키지만 뒷줄에서 다시 일반화하는 경우가 남아 있습니다.

**"컴퓨터"라고만 물었더니 2015년 이미지 인식 논문이 나왔습니다.** LLM이 검색어를 `computer architecture`로 정했고, 제목에 "Architecture"와 "Computer"가 모두 들어 있고 인용이 3만 회가 넘는 *Rethinking the Inception Architecture for Computer Vision*이 2위로 검색됐습니다. PDF가 없는 논문이 빠지면서 이 논문이 후보 맨 앞이 됐고, LLM은 그대로 골랐습니다. 한 단어로는 무엇을 원하는지 알 수 없으니, 지금은 검색 전에 되묻습니다. 대문자 약어(QMIX, RLHF)는 그 자체로 구체적인 기법명이라 그대로 검색합니다.

같은 답변에는 더 위험한 오류가 있었습니다. 원문의 "top-1 **오류율 21.2%**"를 "기존 대비 **21.2% 향상된** 오류율"로 옮긴 것입니다. 숫자는 맞는데 뜻이 정반대라 읽는 사람이 알아채기 어렵습니다. 프롬프트에 수치를 원문 의미대로 쓰라는 규칙을 넣고, 이 오류를 부추기던 출력 예시("기존 방법 대비 D만큼 향상")도 고쳤습니다. 숫자 옆에 "오류율 값 자체"라고 직접 표시도 해봤습니다. 그래도 같은 논문으로 4번 돌리면 4번 모두 틀렸습니다. 원문이 "gains over the state of the art: 21.2% top-1 … error"라서, 2.4B 모델은 이 문장 구조를 이기지 못했습니다. 그래서 막는 대신 **답변이 나온 뒤 원문과 대조**합니다. 답변이 "X% 향상/감소"라고 쓴 수치가 원문에서는 변화량 표현 없이 오류율·손실 같은 지표와 함께만 나오면, 답변 아래에 원문 문장과 함께 경고를 띄웁니다. 잘못 쓴 4건을 모두 잡았고, 원문에 실제 변화량("by 3.2%")이 있는 올바른 문장 6건은 하나도 잡지 않았습니다. 이 과정에서 초록의 소수점이 `21:2%`처럼 콜론으로 깨져 있는 것도 발견해, `%` 앞의 숫자에 한해 되돌리도록 했습니다.

**전체 코드를 다시 훑어보니, 예전에 넣은 장치가 오히려 품질을 깎고 있었습니다.**

- **PDF의 "fi"가 사라지고 있었습니다.** PDF는 "fi", "ff" 같은 글자 쌍을 합자 한 글자(ﬁ, ﬀ)로 저장하는 경우가 많은데, 깨진 문자를 걸러내는 허용 목록에 합자가 없어서 공백으로 바뀌었습니다. 캐시된 논문 40편 중 28편에서 약 1,500곳이 "e cient"(efficient), "classi cation"(classification)처럼 깨져 있었습니다. BM25는 단어가 정확히 일치해야 하니 이런 단어는 검색되지 않았고, LLM도 깨진 단어를 읽고 있었습니다. 합자와 수학용 기울임 문자만 원래 글자로 풀도록 고쳤습니다.
- **고친 내용이 반영되지 않을 수 있었습니다.** 임베딩 캐시가 논문 ID와 청크 개수만 확인해서, 위처럼 정제 방식을 바꿔도 청크 수가 같으면 예전 벡터를 그대로 썼습니다. 캐시 이름에 청크 내용의 해시를 넣었습니다.
- **답변 일부가 잘리고 있었습니다.** 이전 모델 시절 "Thinking: … Answer: …" 형식을 처리하던 코드가 남아 있어서, 답변 본문에 "답변:"이라는 단어가 나오면 그 앞을 통째로 버렸습니다. 지금은 답변 맨 앞에 프롬프트의 "[최종 답변]:"을 따라 쓴 경우만 지웁니다.
- **재검색할 때 핵심어를 피하게 만들었습니다.** 직전 검색어를 "제외할 검색어"로 LLM에 넘기는 장치가 있었습니다. 원래는 모델이 이전 검색어를 재활용하지 못하게 하려던 것인데, Ollama 호출은 매번 기록 없이 시작하므로 재활용할 방법이 애초에 없었습니다. 오히려 검색이 실패한 뒤 사용자가 같은 핵심어로 다시 물으면 그 핵심어를 피하게 만들어서 없앴습니다.
- **"더 알려줘"만으로 후속 질문 처리했습니다.** "강화학습에 대해 더 알려줘"처럼 새 주제를 꺼내도 "더 알려"라는 말 때문에 지금 논문으로 답했습니다. "이 논문", "방금"처럼 지금 논문을 분명히 가리키는 말만 바로 후속 질문으로 보고, 나머지는 LLM이 판단합니다.
- **쓰지 않는 기능을 지웠습니다.** 한 번도 켜지 않았고 영어 전용 모델이던 크로스인코더 재순위화를 지웠습니다.
- **네트워크 대기를 줄였습니다.** Semantic Scholar 호출 간격을 지키려고 매 호출 전에 무조건 1~3초를 쉬던 것을, 직전 호출 이후 남은 시간만 쉬게 바꿨습니다. PDF를 구할 수 있는지 미리 확인하는 단계(Unpaywall 조회)도 한 편씩 차례로 하지 않고 동시에 합니다.

**같은 말을 두 번 했습니다.** "~를 분석합니다"와 "~를 분석하고 있습니다"가 연달아 나오는 식입니다. 이미 로드된 임베딩 모델로 비슷한 줄을 지우려 했는데, 재보니 "계획 능력을 평가합니다"와 "도구 사용 능력을 평가합니다", "일자리를 줄입니다"와 "늘립니다"도 유사도가 0.988로 실제 중복(0.99 이상)과 거의 같았습니다. 임베딩은 문장 구조가 같으면 핵심 단어 하나가 달라도 비슷하다고 봅니다. 그래서 유사도가 높고, **짧은 줄의 단어가 긴 줄에 모두 들어 있을 때만** 중복으로 보고 긴 쪽을 남깁니다. 어미만 다른 반복 5쌍은 모두 잡았고, 내용이 다른 15쌍은 하나도 지우지 않았습니다. 단어를 바꿔 쓴 중복은 잡지 못하지만, 다른 내용을 지우는 것보다는 낫다고 판단했습니다.

**모델은 그대로 두고 속도를 줄였습니다.** 검색된 문단은 1,000자인데 질문에 실제로 답하는 문장은 두세 개뿐인 경우가 많습니다. 이미 로드된 임베딩 모델로 문장별 유사도를 재서 관련 있는 것만 남기니 프롬프트가 30~50% 짧아졌습니다. 새 모델을 올리거나 LLM을 더 부르지 않아 비용이 거의 없습니다. 여기에 답변을 토큰 단위로 흘려보내니 체감 대기 시간이 크게 줄었습니다.

**노트북에 원래 있던 내장 그래픽을 찾아 썼습니다.** 질문 하나에 50초 가까이 걸려서 단계별로 시간을 재보니, 대부분이 LLM이 프롬프트를 *읽는* 시간이었습니다. 논문 선택 단계에서 답을 쓰는 데는 4초인데, 후보 10편의 초록을 읽는 데 13~18초가 걸렸습니다. 이 "읽기"는 GPU가 특히 잘하는 계산이라, 노트북에 기본으로 들어 있는 Intel Iris Xe를 Ollama의 Vulkan 백엔드로 연결했습니다. 읽는 속도가 초당 70토큰에서 340토큰으로 빨라졌고, 같은 입력에서 CPU와 같은 논문을 고르는지(14개 중 13개 일치 — CPU끼리 두 번 돌린 일치율 86%보다 높음)와 한국어 답변이 깨지지 않는지도 확인했습니다. 추가 하드웨어도, 외부 전송도 없이 얻은 개선입니다.

`eval/benchmark_speed.py`로 같은 조건(캐시된 PDF, 질문 3개 중앙값)에서 단계별로 다시 쟀습니다.

| 단계 | CPU | 내장 그래픽 |
|---|---|---|
| 논문 선택 (후보 10편) | 33.9초 | 11.7초 |
| 답변 생성 (현재 설정) | 18.6초 | 9.7초 |

| 답변 설정 (내장 그래픽) | 문맥 길이 | 답변 생성 |
|---|---|---|
| 청크 5개 + 문장 압축 (현재) | 713자 | 9.7초 |
| 청크 5개, 압축 끔 | 4,443자 | 13.9초 |
| 청크 3개 + 문장 압축 | 472자 | 7.5초 |

| 그 밖의 단계 | 시간 |
|---|---|
| 임베딩 모델 로드 | 1.6초 |
| 인덱싱 — 처음 보는 논문 (77청크) | 3.7초 |
| 인덱싱 — 같은 논문 재질문 (임베딩 캐시) | 0.1초 |
| 하이브리드 검색 + 문장 압축 | 0.4초 |

문장 압축이 문맥을 84% 줄여 답변을 4초 앞당기고, 청크를 3개로 줄이면 2초를 더 아낄 수 있지만 근거가 줄어서 5개를 유지했습니다. 이 표에 없는 검색과 PDF 다운로드는 네트워크 상태에 따라 수 배씩 달라져서 같은 조건으로 반복 측정하기 어렵기 때문에 따로 뺐습니다.

같은 측정 과정에서 임베딩 모델이 이미 받아둔 상태인데도 실행할 때마다 Hugging Face 서버에 업데이트를 확인하고 있다는 것도 발견했습니다. 로컬 캐시를 먼저 쓰도록 바꿔 모델 로드가 9초에서 1.6초로 줄었고, 앱을 켤 때 인터넷 연결이 필요 없어졌습니다.

## 검증

자동 점검 스크립트가 두 개 있습니다.

```bash
python eval/healthcheck.py           # 시스템 43개 항목, 약 50초
python eval/run_questions.py         # 질문 10개 자동 실행 후 리포트 생성
python eval/compare_selection.py     # 논문 선택 방식 블라인드 비교
python eval/benchmark_speed.py       # 단계별 속도 측정, CPU·GPU 비교 (약 5분)
```

`healthcheck.py`는 의존성 설치부터 Ollama 응답, 임베딩 차원, BM25 인덱스, RRF 산식, Streamlit 기동까지 확인합니다. "예외 없이 실행됨"이 아니라 실제 출력값을 봅니다. 예를 들어 Ollama 검사는 프로세스를 찾는 게 아니라 실제로 프롬프트를 보내 응답 내용을 확인합니다.

`verify_healthcheck.py`는 각 검사에 **일부러 고장을 주입해서 잡아내는지** 확인합니다. 이 과정에서 통과만 하고 아무것도 못 잡는 검사 세 개를 발견했습니다. RRF 검사는 희귀 단어가 검색되는지만 봤는데 밀집 벡터도 그 단어를 어느 정도 잡아서, 어휘 순위를 빼도 통과해버렸습니다. Streamlit 검사는 앱이 깨져도 서버 셸은 HTTP 200을 돌려줘서 문법 오류조차 놓쳤습니다. 셋 다 고쳤고, 지금은 주입한 고장 74개를 모두 검출합니다.

검사는 함수가 올바른지와 별개로 **그 함수가 실제로 호출되는지**도 봅니다. 함수 자체는 멀쩡한데 호출하는 줄이 빠지면 단위 검사는 전부 통과하기 때문입니다. 예를 들어 BM25 검사는 검색 단계가 실제로 넘기는 값을 가로채서 영어 키워드가 들어 있는지 확인하고, 전체 파이프라인 검사는 인덱스에 참고문헌 청크가 남아 있지 않은지 확인합니다.

`compare_selection.py`는 논문 선택 방식을 바꿀지 판단할 때 썼습니다. 속도를 위해 후보를 임베딩 상위 3편으로 줄이는 안을 검토했는데, 먼저 현재 방식을 같은 후보로 두 번 돌려 **자기 일치율(86%)**을 쟀습니다. 현재 방식도 원래 들쭉날쭉하다면 다른 논문을 고른 것만으로는 품질 저하라고 볼 수 없기 때문입니다. 절충안은 79%의 질문에서 다른 논문을 골랐고 시간은 4.5초밖에 줄지 않아, 적용하지 않았습니다. 두 방식의 선택을 A/B로 섞은 블라인드 비교 파일도 만들어줍니다.

## 실행

Ollama가 설치되어 있어야 합니다.

```bash
pip install -r requirements.txt
ollama pull exaone3.5:2.4b
```

터미널 두 개가 필요합니다.

```bash
ollama serve
streamlit run app.py
```

환경변수는 전부 선택 사항이지만, 없으면 기능이 일부 제한됩니다.

| 변수 | 없을 때 |
|---|---|
| `S2_API_KEY` | 공유 요청 풀을 쓰게 되어 429가 자주 발생합니다. [무료 발급](https://www.semanticscholar.org/product/api#api-key-form) |
| `UNPAYWALL_EMAIL` | PDF 확보 단계에서 Unpaywall을 건너뜁니다. 이메일만 넣으면 되고 승인 절차는 없습니다 |
| `CORE_API_KEY` | CORE 단계를 건너뜁니다 |
| `OLLAMA_NUM_GPU` | Ollama 기본값을 씁니다. `0`으로 두면 CPU로만 돌립니다(내장 그래픽 드라이버에 문제가 있을 때) |

i7-1355U(Iris Xe 내장 그래픽) + 16GB RAM에서 개발했습니다. 전용 그래픽카드는 필요 없습니다.

내장 그래픽 가속을 쓰려면 Ollama를 실행하기 전에 환경변수 두 개를 설정하고 Ollama를 재시작하세요.

```powershell
[Environment]::SetEnvironmentVariable("OLLAMA_VULKAN", "1", "User")
[Environment]::SetEnvironmentVariable("OLLAMA_IGPU_ENABLE", "1", "User")
```

질문을 하나 던진 뒤 `ollama ps`의 `PROCESSOR`가 `100% GPU`로 나오면 적용된 것입니다. 설정하지 않거나 내장 그래픽이 없으면 CPU로 동작하고, 질문 1회에 50초 안팎이 걸립니다. 노트북은 전원을 연결한 상태에서 쓰는 걸 권합니다.

## 한계

**논문을 한 번에 한 편만 인덱싱합니다.** 새 논문을 넣으면 이전 것은 지워집니다. 한 편을 깊이 보는 데는 유리하지만, "이 분야의 주류 접근법은?"처럼 여러 논문을 종합해야 하는 질문에는 답할 수 없습니다. 엄밀히 말하면 여러 문서에서 근거를 모으는 RAG 본래 형태라기보다 단일 문서 질의응답에 가깝습니다. 다중 논문 인덱싱이 다음 과제입니다.

**네트워크 단계의 속도는 재지 못했습니다.** 로컬 단계는 `benchmark_speed.py`로 같은 조건에서 반복 측정하지만, Semantic Scholar 검색과 PDF 다운로드는 와이파이 상태에 따라 크게 달라져 같은 조건을 만들 수 없습니다. 학교처럼 네트워크가 느린 곳에서는 질문 1회 시간의 대부분이 이 부분입니다. 내장 그래픽 가속도 아직 짧은 기간만 써봤기 때문에, 오래 켜두었을 때의 안정성은 더 지켜봐야 합니다.

**"제일 최신"은 검색된 후보 안에서의 최신입니다.** Semantic Scholar 검색 API는 날짜순 정렬을 지원하지 않아서, 올해 논문 중 관련도 상위 10편을 받은 뒤 그 안에서 가장 최근 것을 고릅니다. 그해 전체에서 가장 마지막에 나온 논문이 아닐 수 있고, 무료 PDF가 없는 논문은 후보에서 빠집니다.

**후보 목록은 가장 최근 검색 한 번분만 고를 수 있습니다.** 지난 검색의 후보는 대화 기록에서 볼 수는 있지만 버튼이 없습니다. 다시 답하기는 그 검색의 원래 질문으로만 하고, 새 논문을 받는 동안(다운로드 + 인덱싱 + 답변, 15초 이상)은 기다려야 합니다.

**답변 범위 규칙과 중복 제거는 부분적으로만 동작합니다.** 트렌드 질문에서 첫 줄은 "이 논문은"으로 범위를 밝히지만, 뒷줄에서 다시 분야 전체처럼 말하는 경우가 남아 있습니다. 중복 줄 제거는 어미만 다른 반복만 잡고, 단어를 바꿔 쓴 반복은 그대로 둡니다.

**모델이 모르는 신조어는 여전히 약합니다.** 약어는 되살리도록 했지만, 약어가 아닌 새 용어(예: 최근에 생긴 기법 이름)는 키워드 단계에서 엉뚱하게 바뀔 수 있습니다. 질문을 검색어로 바꾸는 단계가 모델의 학습 시점에 묶여 있는 한 남는 문제입니다.

**검색어 3개 중 사실상 첫 번째만 쓰입니다.** 검색어 순서대로 검색하다 후보 10편이 차면 멈추는데, 실측해보니 대부분 첫 검색어 하나로 10편이 채워졌습니다. 검색어마다 몇 편씩 나눠 받으면 후보가 다양해지겠지만, 첫 검색어의 정확한 결과가 줄어드는 대가가 있어 아직 바꾸지 않았습니다.


**답변이 논문과 맞는지는 자동으로 판정할 수 없습니다.** 검색 결과 개수나 출력 형식처럼 객관적인 부분은 검사할 수 있지만, 환각 여부는 결국 사람이 읽어야 합니다. 수치 검사는 "지표 값을 변화량으로 바꿔 쓴" 한 가지 유형만 잡고, 잡아도 고치지는 않고 경고만 합니다. "17.3%로 개선되었다"처럼 변화 표현이 숫자에 바로 붙지 않은 문장도 놓칩니다.

**한 단어 질문은 구체적인 단어여도 되묻습니다.** "트랜스포머"처럼 그 자체로 충분히 구체적인 단어도 넓은 단어("컴퓨터")와 구별하지 못해 되묻습니다. 단어의 범위를 판단하려면 모델의 지식이 필요한데, 그 판단을 소형 모델에 맡기면 오히려 틀릴 수 있어 "그대로 검색" 버튼을 둬서 클릭 한 번으로 넘어가게 했습니다.

**EXAONE 3.5는 비상업 라이선스입니다.** 학술·개인 용도는 허용되지만 상업적 사용에는 LG AI Research와 별도 계약이 필요합니다.

## 개발 방식

코드는 Claude Code를 사용해 작성했습니다. 제가 한 일은 다음과 같습니다.

- 문제 정의와 요구사항 설계 (전용 GPU 없는 노트북이라는 제약 아래에서의 로컬 RAG 시스템)
- 아키텍처 결정 — 검색 소스 전환, 임베딩 모델 선정, 하이브리드 검색 도입, 파이프라인 구조
- 실제 질의를 반복해서 돌려보며 문제를 찾고 원인을 진단, 프롬프트 개선
- 검증 체계의 범위와 판정 기준 설계
- 발표 자료 및 평가표 작성
