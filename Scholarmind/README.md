ScholarMind
논문을 찾아 읽고 답해주는 RAG 어시스턴트입니다. 현재 저의 노트북 CPU만으로 돌아가게끔 설계했습니다.

질문을 입력하면 Semantic Scholar에서 관련 논문을 검색하고, 신뢰도를 따져 한 편을 고른 뒤, PDF를 받아 인덱싱하고 그 내용에 근거해서 답합니다. 
클라우드 API로 추론하지 않기 때문에 질문 내용이 외부 모델 서버로 나가지 않습니다.

졸업 캡스톤 Ragxiv의 후속 버전입니다. Ragxiv는 arXiv에서만 검색했는데, 실제로 써보니 세 가지가 걸렸습니다. 
심사를 거치지 않은 논문이 대부분이라 신뢰도를 판단할 수 없었고, 의미 기반 검색만으로는 약어나 고유명사를 놓쳤으며, 답변이 완성될 때까지 화면이 멈춰 있었습니다. 이 버전은 그 셋을 해결한 결과입니다.

-동작 방식-
"방금 논문 요약해줘" 같은 후속 질문이면 새로 검색하지 않고 이미 인덱싱된 논문을 쓰며, 키워드로 대부분 걸러내고 애매할 때만 LLM에 물어봅니다.

새 주제라면 이렇게 진행합니다.

1. LLM이 질문을 검색용 영어 키워드 3개로 바꿉니다.
2. 구문별로 나눠 Semantic Scholar를 검색하고 결과를 병합합니다.
3. 신뢰도 필터로 후보를 거르고, PDF를 구할 수 없는 논문은 미리 제외합니다.
4. LLM이 초록을 읽고 한 편을 고릅니다.
5. PDF를 받아 1,000자 단위로 쪼개고 FAISS와 BM25에 넣습니다.
6. 두 검색 결과를 합쳐 상위 3개를 고르고, 질문과 관련된 문장만 남겨 LLM에 넘깁니다.
7. 답변을 토큰 단위로 출력하면서 출처를 함께 보여줍니다.

-구성-
추론	Ollama + EXAONE 3.5 2.4B (로컬, CPU)
임베딩	intfloat/multilingual-e5-small (384차원)
검색	FAISS IndexFlatIP + BM25, RRF로 융합
논문	Semantic Scholar API
PDF	arXiv · openAccessPdf · Unpaywall · CORE 순차 시도, PyMuPDF로 추출
UI	Streamlit

-만들면서 겪은 애로사항들-
검색이 실패하는데 원인을 알 수 없었습니다.
같은 질문이 어떤 날은 결과를 가져오고 어떤 날은 "논문을 찾을 수 없다"고 나왔습니다.
API를 직접 호출해보니 429였습니다.
Semantic Scholar는 API 키 없이 쓰면 전 세계 사용자가 공유하는 요청 풀에 들어가는데, 거의 항상 포화 상태였습니다.

문제는 코드가 429를 받으면 그냥 빈 목록을 반환했다는 점입니다.
호출한 쪽에서는 "논문이 없다"와 "API가 막혔다"를 구분할 수 없었고, 결국 사용자에게 "질문을 바꿔보세요"라고 잘못 안내하고 있었습니다.
지금은 429를 별도 예외로 올려서 화면에 요청 한도 초과라고 정확히 표시하고, 첫 실패에서 즉시 중단해 남은 할당량을 낭비하지 않습니다.

의미 검색만으로는 부족했습니다. 밀집 벡터는 "환각"과 "hallucination"이 같은 뜻인 걸 알아채지만, QMIX 같은 알고리즘 이름은 의미로 압축하는 과정에서 뭉개집니다.
그래서 단어를 그대로 세는 BM25를 함께 돌리고 두 순위를 RRF로 합쳤습니다. 점수 체계가 서로 달라 그냥 더할 수 없는데, RRF는 점수 대신 등수만 쓰기 때문에 정규화가 필요 없습니다. BM25는 신경망이 아니므로 CPU 부담도 거의 없습니다.

요약을 시켰더니 부록을 요약했습니다. 진화 전략을 다루는 논문에 "요약해줘"라고 했더니 "이 논문은 강화학습 하이퍼파라미터 조합에 초점을 맞춥니다"라고 답했습니다. 부록의 실험 설정 표가 검색된 것이었습니다. 
원인은 "요약해줘"라는 말 자체에 검색할 단서가 없다는 점이었습니다. 유사도 검색이 사실상 아무 문단이나 집어온 겁니다. 지금은 요약 의도가 감지되면 유사도 검색을 건너뛰고 문서 앞부분을 씁니다.

한국어 답변만 형식을 안 지켰습니다. 프롬프트에 불릿으로 쓰고 번호는 쓰지 말라고 했는데, 영어는 지키고 한국어만 매번 1. 2. 3.으로 나왔습니다. 소형 모델이 한국어 생성에서 형식 지시를 놓치는 것 같았습니다. 프롬프트에 출력 예시를 넣고, 그래도 번호가 나오면 후처리로 바꾸도록 했습니다. 다만 3.5배 같은 소수점이 망가지지 않게 줄 맨 앞에만 적용합니다.

외부 데이터가 틀린 경우도 있었습니다. Semantic Scholar가 알려준 arXiv 번호가 전혀 다른 논문을 가리키는 사례를 만났습니다. 화면에는 A 논문 제목이 뜨는데 저자와 연도는 B 논문 것이었습니다. 남의 데이터베이스라 고칠 수는 없지만 탐지는 됩니다. arXiv 번호는 앞 네 자리에 제출 연월이 들어 있어서, 논문의 게재 연도와 대조하면 어긋나는 걸 잡을 수 있습니다. 차이가 크면 인용 정보 옆에 경고를 띄웁니다.

모델은 그대로 두고 속도를 줄였습니다. 검색된 문단은 1,000자인데 질문에 실제로 답하는 문장은 두세 개뿐인 경우가 많습니다. 이미 로드된 임베딩 모델로 문장별 유사도를 재서 관련 있는 것만 남기니 프롬프트가 30~50% 짧아졌습니다. 새 모델을 올리거나 LLM을 더 부르지 않아 비용이 거의 없습니다. 여기에 답변을 토큰 단위로 흘려보내니 체감 대기 시간이 크게 줄었습니다.

-검증-
자동 점검 스크립트가 두개 있습니다.

python eval/healthcheck.py     # 시스템 23개 항목, 약 40초
python eval/run_questions.py   # 질문 10개 자동 실행 후 리포트 생성
healthcheck.py는 의존성 설치부터 Ollama 응답, 임베딩 차원, BM25 인덱스, RRF 산식, Streamlit 기동까지 확인합니다. "예외 없이 실행됨"이 아니라 실제 출력값을 봅니다. 예를 들어 Ollama 검사는 프로세스를 찾는 게 아니라 실제로 프롬프트를 보내 응답 내용을 확인합니다.

verify_healthcheck.py는 각 검사에 일부러 고장을 주입해서 잡아내는지 확인합니다. 이 과정에서 통과만 하고 아무것도 못 잡는 검사 세 개를 발견했습니다. RRF 검사는 희귀 단어가 검색되는지만 봤는데 밀집 벡터도 그 단어를 어느 정도 잡아서, 어휘 순위를 빼도 통과해버렸습니다. Streamlit 검사는 앱이 깨져도 서버 셸은 HTTP 200을 돌려줘서 문법 오류조차 놓쳤습니다. 셋 다 고쳤고, 지금은 주입한 고장 29개를 모두 검출합니다.

-실행-
Ollama가 설치되어 있어야 합니다.

pip install -r requirements.txt
ollama pull exaone3.5:2.4b
터미널 두 개가 필요합니다.

ollama serve
streamlit run app.py
환경변수는 전부 선택 사항이지만, 없으면 기능이 일부 제한됩니다.

-변수 없을 때-
S2_API_KEY	공유 요청 풀을 쓰게 되어 429가 자주 발생합니다. 무료 발급
UNPAYWALL_EMAIL	PDF 확보 단계에서 Unpaywall을 건너뜁니다. 이메일만 넣으면 되고 승인 절차는 없습니다
CORE_API_KEY	CORE 단계를 건너뜁니다
RERANK_ENABLED	1로 두면 크로스인코더 재순위화를 켭니다. 기본은 꺼짐
i7-1355U + 16GB RAM에서 개발했습니다. GPU는 필요 없지만 CPU 추론이라 답변 생성에 수십 초가 걸립니다.

-한계-
논문을 한 번에 한 편만 인덱싱합니다. 새 논문을 넣으면 이전 것은 지워집니다. 한 편을 깊이 보는 데는 유리하지만, "이 분야의 주류 접근법은?"처럼 여러 논문을 종합해야 하는 질문에는 답할 수 없습니다. 엄밀히 말하면 여러 문서에서 근거를 모으는 RAG 본래 형태라기보다 단일 문서 질의응답에 가깝습니다. 다중 논문 인덱싱이 다음 과제입니다.

속도 개선을 수치로 재지 않았습니다. 프롬프트가 짧아진 것과 캐시 효과(검증 스크립트 기준 41초 → 14초)는 확인했지만, 각 조치가 실제로 몇 초를 줄였는지는 측정하지 못했습니다.

크로스인코더 재순위화는 켜본 적이 없습니다. 구조만 구현해뒀고 효과는 검증하지 않았습니다. 기본 모델이 영어 중심이라 한국어 질의가 주 사용 사례인 이 프로젝트와는 잘 맞지 않아, 쓰려면 다국어 모델로 바꾸는 것까지 함께 봐야 합니다.

답변이 논문과 맞는지는 자동으로 판정할 수 없습니다. 검색 결과 개수나 출력 형식처럼 객관적인 부분은 검사할 수 있지만, 환각 여부는 결국 사람이 읽어야 합니다.

EXAONE 3.5는 비상업 라이선스입니다. 학술·개인 용도는 허용되지만 상업적 사용에는 LG AI Research와 별도 계약이 필요합니다.

-개발 방식-
코드는 Claude Code를 사용해 작성했습니다. 제가 한 일은 다음과 같습니다.

문제 정의와 요구사항 설계 (로컬 CPU 환경이라는 제약 아래에서의 RAG 시스템)
아키텍처 결정 — 검색 소스 전환, 임베딩 모델 선정, 하이브리드 검색 도입, 파이프라인 구조
실제 질의를 반복해서 돌려보며 문제를 찾고 원인을 진단, 프롬프트 개선
검증 체계의 범위와 판정 기준 설계
발표 자료 및 평가표 작성
라이선스
저장소에 논문 PDF나 저작권 자료는 포함하지 않습니다. 코드는 개인·학술 목적으로 자유롭게 쓰셔도 됩니다.
